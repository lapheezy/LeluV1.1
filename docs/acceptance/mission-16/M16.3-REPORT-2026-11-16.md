## 4. The three defects that made "visible, manipulable" false

Each was diagnosed from evidence, not guessed.

### 4.1 The dock threw on every press

**Symptom:** the dock's buttons looked dead.
**Cause:** `getWorldDirection` was handed a plain-object camera shim, so
`target.set(...).normalize()` threw `TypeError: ... normalize is not a function`
on the first press and aborted the handler.
**Fix:** store the camera's `getDirection()` and hand the renderer a real
`THREE.Vector3`.

### 4.2 The renderer refused to paint at all in this container

**Symptom:** geometry existed in the scene graph, nothing appeared on screen.
**Cause:** the scene governor sets `frameloop="never"` when it believes the
machine is software-rendered and the profile is `"light"`:

```ts
const paintWorld = (!softwareGL || perfWorld) && profile !== "light";
```

This container has no GPU, so `profileFor()` returns `"light"` and the second
conjunct is false — **even with `?perf-world`**, which only lifted the first.
**Fix:** `forceWorld = Boolean(perfWorld)` lifts both refusals, dev-only and
stripped from production builds. This is why every previous "the mesh is in the
graph" claim had no pixels behind it: nothing was ever drawn.

### 4.3 The projection probe is on demand, not per frame

`window.__leluCreativeScreen()` projects each creation's bounding-box centre
through the live camera when called. Useful, but as §6 records, it is not
reliable enough to drive an automated pointer test on its own.

## 6. What is *not* proven, stated plainly

**Selection and drag by pointer (O3) are PARTIAL, not VERIFIED.** The
implementation exists — window-capture pointerdown, raycast against the
creative root, gesture mutex so a drag moves the object or the camera but never
both, commit-on-release to the canonical store. But the automated attempt to
prove it with a real pointer failed, and the reason is worth recording:

1. A press on a creation does not land on our canvas. The scene's canvases are
   stacked and the Cosmos covers the world with its own interactive navigation
   surface, so the press lands on a `DIV` above us. A canvas-target-only guard
   therefore rejected every real tap (`selection` never became non-null from a
   click, only from the build itself).
2. After widening the guard to "any press that is not a control", the press
   reached the raycast — and missed (`hits: 0`) at the object's projected
   point. The chair's origin is the floor between its legs, so the ray passed
   through empty space; an adaptation that aims at the bounding-box centre was
   added, but by then the projection and the flying camera disagreed enough
   that the harness could not place the cursor on the mesh reliably.

So the mechanism is implemented and the projection probe exists, but **no
screenshot in this repository yet shows a click selecting the chair**. O4's
in-app detach/undo/restore/reload proof is in the same position: the engine
tests pass, the pointer-level proof does not exist.

**Mobile (O9) and physical iPhone Safari (O10):** no hardware, no mobile layout
pass. Desktop browser emulation would not make this claim true even if it had
been run.
