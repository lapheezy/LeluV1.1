## 4. The context model

`src/core/couture/continuity.ts` answers one question per turn: **which creation
does this instruction refer to?**

| Distinction | How it is held | Authority |
|---|---|---|
| Explicitly named ("the chair") | the noun in the instruction | `intents.ts` (unchanged) |
| Last **mentioned** | newest `obj-…` id in `AIRequest.messages` | conversation text |
| Last **worked on** | `conversationId → objectId`, written only by a successful tool result | `rememberCreativeReferent` |
| Currently **selected** | `getCreativeSelection()` | core selection channel |
| **Currently** valid | `store.get(id)` and not archived | `CreativeObjects` |

Resolution order is: explicit noun → conversation text → per-conversation
record → live selection. Every candidate is validated against the store on every
read, so a deleted, archived or unknown id is dropped rather than acted on. "The
most recently created object" is never assumed.

The per-conversation record is a bounded map (50 conversations, 2-hour age cap)
keyed by `conversationId`, which **is** the isolation: two chats cannot share a
referent because they cannot share a key. It is not a memory system and it is
not an object store — it holds one id per conversation and re-validates it.

## 5. Isolation, staleness and ambiguity

| Case | Behaviour | Evidence |
|---|---|---|
| Two conversations, same process | no referent crosses over; chat B resolves nothing | TEST `two conversations do not share a referent` |
| Id mentioned then deleted | mention is skipped; the next valid mention or selection is used | TEST `a stale id is skipped` |
| Id archived | never a referent | TEST `an archived object is not a referent` |
| Empty conversation | no referent invented | TEST `an empty conversation invents nothing` |
| Implicit reference with **no** referent | the tool is called with `"it"` and refuses with the object list | TEST `with no referent the tool is asked to refuse, not to guess` |
| Two objects match a name | refused, `matches 2 objects` (WP03 behaviour retained) | DISPATCH |

The "no referent" case deliberately produces a call the tool rejects, because
silence compiles to a reply that looks like success. An explicit noun always
wins over the conversation: "rotate **the pendant**" after working on the chair
moves the pendant.

## 6. Execution: why the operation now runs

`src/core/AIRouter.ts` already had the precedent that a deterministic
construction runs even when a provider is reachable. A canonical creative
operation is the same kind of claim — "rotate it 90 degrees" either rotated that
object in the store or it did not — so a plan made only of `couture.objects`
steps now takes the direct route (`reason: "creative"`). The reply says so:
*"Done on the creation itself, not described: …"*.

This is the change that closed the live symptom. Without it, a reachable model
answered the turn with prose while the object never moved — the exact failure
WP03's live run recorded.

## 7. Compound and sequential execution

`DirectPlan` keeps the clause order, each step resolves its own object, and each
step is dispatched through the same gate. A failing step now poisons only what
depends on it: later steps that target the **same object** are not attempted and
are listed as `↷ … not attempted: an earlier step on <id> failed`, while steps on
other objects still run, because they are independent. The reply states the split
plainly (`N of M attempted steps succeeded; K not attempted …`), and
`metadata.steps` carries `{ ok, skipped, reason }` per step, so the partial result
is machine-readable rather than inferred from prose. A step is never retried on
behalf of a later one.

Idempotency: selection is a pointer and does not bump the object revision
(asserted in WP03 and still asserted); transforms are absolute for absolute
requests, so a repeated identical instruction is a no-op rather than an
accumulation. Destructive actions are never retried (§9).

## 8. The verification contract

`src/core/couture/verification.ts` judges an operation on four separate
conditions, and never lets one stand in for another:

| Condition | Question | Class |
|---|---|---|
| target | is the object that changed the object that was meant? | STORE |
| change | did the store record a change (or, for selection, provably none)? | STORE |
| value | is the resulting position / rotation / scale the requested one? | STORE |
| preserved | were the fields the operation must not touch left alone? | STORE |
| persisted | is that state written through the store's persistence? | PERSISTED |

Status rules: any failure of target, change or value is **FAILED**; a failure of
only "preserved" or "persisted" is **PARTIAL**; everything green is **VERIFIED**.
`evidence` is `"STORE"` — deliberately not "visual". Geometry and rendering are a
different class and are reported separately (§11).

A FAILED verification now also makes the tool result `ok: false` and says
`verification failed: …` in its content. A store call that returned an object is
no longer sufficient to report success.

## 9. Bounded, safe correction

The executor retries **once**, and only when all of these hold: the operation is
a transform with a known absolute target, verification came back FAILED, and the
store recorded no change at all. Selection, focus, duplicate and every
destructive action are excluded — there is nothing idempotent to repeat. A second
failure is reported as a failure; there is no loop and no escalation.

Failure injection (real tool, real store, one dropped write) proves both halves:
the retry recovers and the operation reports VERIFIED with
`correction: { attempted: true, tries: 2 }`; a permanent fault ends at exactly
two attempts with `ok: false`, `status: "FAILED"` and an unchanged object.

## 14. Performance

Referent resolution is a reverse scan of the turn's messages for an id pattern,
then one `store.get` — no network, no model call. The per-conversation map is
pruned on write. Verification adds a small number of array comparisons per
operation. The live run's turn latency was dominated by provider attempts, not by
this code path.
