### Finding A — spatial command routing (traced in code, reproduced in the app)

Path: user text → `DirectResolver.directPlanFor` → { `workspacePlan` → `parseWorkspaceCommand` } and { `compileDirect` → `cosmosPlan` } → `DirectResolver.execute` → `dispatchToolCall` → `cosmos.object.position` → `CosmosObjectStore.transform`.

1. **The precedence rule ignored what the names are.** With objects in the Cosmos, `cosmosPlan` already produced a correct `cosmos.object.position {object: "gear", near: "cabin"}`. `parseWorkspaceCommand` also read "next to" as a split layout (`{mode: "split", open: []}`), and `directPlanFor` gave **every** non-stage workspace plan precedence over the creative/object plan. So `workspace.arrange` ran, the windows split, and the gear did not move. M17.2 reproduced this: provider `lelu-direct`, `["workspace.arrange:done"]`, gear unchanged.
2. **Too few phrasings.** `cosmosPlan` knew only "next to / beside / near / by / behind / above / in front of", always placing at +x. "To the left of", "closer to" and "farther away" produced no plan, and the tool had no relation parameter.
3. **Names were guessed.** `CosmosObjectStore.resolve` returns the newest partial match, so after a duplicate "the gear" silently meant the copy (M17.2 F2).

## WP01 — Spatial intelligence

### What changed (existing systems, extended)

- **`core/cosmos/objects/spatialIntent.ts`** (new, pure: no store, tools or model).
  - `parseSpatialIntent` reads, from a sentence:
    - relative placement: next to / beside / near / to the left of / to the right of / in front of / behind / above / below;
    - distance: closer to / farther (away) (from), "a little" / "a lot";
    - direction: left / right / forward / backward / up / down, "by N".
  - `placeRelative` and `placeDirection` compute positions in the **existing** conventions:
    - world frame, as `CosmosObjectsLayer` draws `frame.position`;
    - +x right, +y up, +z toward the viewer;
    - "beside" is the existing 1.4 × scale reach on +x.
  - "Closer" halves the gap. It may come inside the beside spacing, but never nearer than 0.6 of it (never into the reference).
- **`CosmosObjectStore.match(ref)`** (new method; `resolve()` is unchanged for every other caller).
  - Matches in tiers: id → whole name → a word of the name → what it was built as (builder/domain, e.g. "the gearbox") → part of the name.
  - It returns **all** candidates in the strongest tier, so a caller can ask instead of guessing.
- **`CosmosObjectStore.transform`** takes an optional `note` and `ref` for its provenance step.
  - A placement records what it was placed against, which is how "farther away" finds its reference.
  - The Neural Map draws lineage only from duplicated/extracted steps, so a move never becomes a relation.
- **`cosmos.object.position`** (the existing tool, extended) gains `relation`, `direction`, `degree` and `distance`.
  - Names are resolved with `match`. When several objects answer, **nothing moves** and the result names the candidates and asks which one.
  - Unknown names are refused.
  - A move that changes nothing says so instead of claiming a move.
  - It never attaches, detaches, regroups, duplicates or touches lineage.
- **`DirectCompiler.cosmosPlan`** uses the parser in place of its single "next to" rule.
- **`DirectResolver.directPlanFor`** is now object-aware:
  - every name in the object plan resolves to a live Cosmos object → **object operation**;
  - the sentence names no window but does name a Cosmos object ("move the spaceship next to the cabin") → object operation, and the tool refuses the unknown name;
  - otherwise the windows keep it ("put the browser next to the chat", "tile my windows").
- **Reply wording:** a refused or ambiguous object operation now begins **"Not done — nothing in the Cosmos changed…"**. It used to begin "Done locally…" above a ✗.

No new store, coordinate system, tool, dispatcher, graph or model call.

### Limits

- **Direction words:** they are world axes, not camera-relative. "Left" is −x even when the camera has turned. The Cosmos has no camera-relative convention to reuse, and inventing one is out of scope.
- **Object categories:** resolution uses names plus the builder and domain the store keeps. There is no synonym table: "the machine" does not find a gearbox.
- **Attached objects:** moving an attached object keeps it attached (TEST). Whether moving a *parent* carries its children was not tested in M17.3.

## WP02 — World continuity and restoration

### B.1 Reproduction

- **Opened directly, the transition works.** One LÉLU opened directly (`InterfaceCompositionStore.open`), then Room → Cosmos → Room → Cosmos, restored correctly every time:
  - the world (`genesis-v1`, 2 canvases) mounts;
  - Genesis V2 unmounts;
  - the companion goes from `world/hidden` back to `planned/visible`.
- **The M17.1 sequence (Original LÉLU + Room first, closed, then One LÉLU) also reaches the correct state, but late.**
  - Sampled at 1, 3, 6 and 10 s after pressing Cosmos in the Room, it was still in the Room at 1 s **and at 3 s** (scroller at 972 px, unmoved).
  - It was correct by 6 s: Cosmos current, world mounted, Room unmounted, companion visible.
  - M17.1 samples once, at exactly 3 s, so it recorded the three failures.

### B.2 Cause

- **Who owns which state.** These were confirmed in code and in the page; no competing store was added:

| State | Owner |
|---|---|
| Open composition and current interface | `InterfaceCompositionStore` |
| What is shown and live | `InterfaceJourney` (IntersectionObserver → `liveRegions`) |
| Scene mount | `InterfaceRegion` (lives or dies with the region) |
| Objects | `CosmosObjectStore` |
| Places | `CosmosNavigation` |
| Companion presence | `useComposedRoomPresented` |

- **What was ruled out.** It is not stale state, a missing remount, the wrong world being selected or a lost active space: every check, once settled, showed the correct world and the objects intact.
- **Measurement** (frame rate and long tasks over 3 s windows):
  - this container has no GPU, so WebGL runs in software at **1–3 fps everywhere** (a fresh Home included);
  - in the Room a single frame takes up to **2.2 s**.
- **Mechanism.** A jump between regions is a smooth scroll, and a smooth scroll advances one step per frame. The Room being left kept rendering until the scroll had carried it out of view, so leaving it took many expensive frames.
  - Room → Cosmos: 4–14 s.
  - Cosmos → Room: 1–2 s, because the Cosmos frames are cheaper.
- **Classification:** a rendering-lifecycle cost during the transition, not a restoration defect.
  - The same three M17.1 failures occur on the pre-M17.2 base `b827c78` (separate worktree and server), so they are **pre-existing**, not a regression.

### B.3 Fix (lifecycle, not a timeout)

- **`InterfaceJourney`:** when a jump leaves a 3D region (a catalog entry with `webgl: true`), that region stops being live **at the jump** rather than after the scroll.
  - Its existing lifecycle applies: the region unmounts as it does today once out of view.
  - The scroll then runs on cheap frames, and the destination mounts as soon as it becomes current.
  - The region is live again the moment it is current again (or after 8 s if the scroll never happened).
- **Untouched:** no new world state, no world rebuilt, no change to identity, cognition, objects or the Neural Map.
