## 1. Flow

There is one client, the existing `SupabasePersistence` client. No second auth path was added.

1. The gate collects an email address only.
2. `SupabasePersistence.requestEmailSignIn(email)` calls:

```ts
client.auth.signInWithOtp({
  email,
  options: {
    shouldCreateUser: true,
    emailRedirectTo: `${window.location.origin}${window.location.pathname}`,
  },
});
```

3. Supabase sends its normal sign-in email. If the project's template includes a one-time code, the gate accepts it and calls `verifyOtp({ email, token, type: "email" })`.
4. The magic link returns to the same origin. The existing client has `detectSessionInUrl: true`; `getSession()` restores the session into the existing browser storage.
5. A cancelled/expired link is read from the non-secret `error` / `error_description` fields and shown as a useful message. The fragment is removed and no token is retained in UI state.

No password is collected, stored, transmitted or requested. `signInWithPassword` remains only in the older persistence API for backward compatibility, but no UI or harness calls it.

## 2. Error handling

The shared helper maps:

| Condition | Message |
|---|---|
| sign-ups disabled | project does not allow email sign-up; ask the owner |
| rate limited | wait before requesting another |
| invalid/expired link or code | request a new one |
| invalid email | enter a valid address |
| network failure | could not reach Supabase |
| invalid API key | deployment key/project mismatch |

The submitted address and token-shaped fragments are redacted from any residual diagnostic. The helper never logs, stores or creates a client.

## 4. Harnesses

`scripts/m145-browser-session.mjs`:

- opens the app in Chromium;
- fills only the email;
- clicks the email sign-in button;
- waits for the normal link to be completed in that browser;
- reads the resulting session from localStorage into memory;
- never logs, writes or returns it to an artifact.

`scripts/verify-m145-real-cloud.ts` restores that session into two independent Supabase clients. `scripts/verify-m145-two-profile.mjs` authenticates profile A this way and creates profile B as an independent context seeded once from A's real storage state. Both require `LELU_M145_HEADFUL=1` for a human to complete the inbox step.

## 5. Tests

`tests/email-auth.test.ts` — 20/20 pass:

- request sends the normalized address, same-origin redirect and sign-up-capable option;
- invalid address makes no request;
- disabled sign-up, rate limit, expired code, network and invalid-key messages;
- code verification trims and uses `type: "email"`;
- cancelled versus expired callbacks;
- a successful token callback exposes no token;
- diagnostics redact address/token text;
- helper has no storage, logging or second client;
- gate/settings contain no password field or password sign-in;
- the real-cloud guard requires opt-in and refuses production or a mismatched ref;
- both harnesses are passwordless and the browser helper never writes/logs a session;
- no session exists before verification, and the persistent client restores from the callback URL;
- runtime session material is gitignored;
- the two-profile harness creates a second independent context and closes the browser.
