# M14.4 — WP07 Cloud Reconnect and Recovery

**Status:** Local transition handling and deterministic recovery **VERIFIED**. Real authenticated Supabase reconnect is **BLOCKED**: no authorized test project, account or credentials are present in this environment.  
**Implementation:** `ContinuityEngine`, `SupabaseContinuityTransport`, `SupabasePersistence` session wiring.

---

## 1. Lifecycle

```text
local-only boot
  -> local writes + durable outbox
  -> network/session unavailable: authentication_required | cloud_unavailable
  -> authenticated session: pull, compare, conflict or apply
  -> conditional upload of the exact local revision
  -> ack: synced for that revision only
  -> reload: outbox and conflict records survive
```

The engine starts at bootstrap with a Supabase transport object but opens no connection. `SupabaseContinuityTransport.availability()` returns:

- `cloud_unavailable` when the browser reports offline;
- `authentication_required` when `SupabasePersistence.continuitySession()` is null;
- `ready` only when the existing persistence layer reports a connected session.

`SupabasePersistence.continuitySession()` deliberately requires the connected state, so a continuity upload cannot race hydration with an unverified identity. Usage accounting continues to use its separate `usageChannel()` because budgets must still apply during a hydration timeout.

## 2. Required transitions

| Transition | Implementation | Result |
|---|---|---|
| Fresh local install, no credentials | Engine starts, seeds authorities, queues local revisions; transport reports auth required | Local app works; no cloud request |
| Existing local data, no credentials | First observation adopts each record with a hash and pending operation | Existing data readable; pending work visible |
| Offline operation | Writes persist immediately; outbox stores exact payload | Local chat/projects/cognition continue |
| Authenticated cloud available | `SupabasePersistence.applySession()` starts/synchronizes the engine after `attachRuntime()` | Pull then conditional push |
| Pending local changes upload | `processOutbox()` bounded batches | Only exact revisions acknowledged |
| Remote changes download | `pullAll()` compares base hash/revision | Newer remote applied; both-changed is conflict |
| Network drops mid-sync | Transport throws or availability changes; operation stays pending | No false global synced state |
| Reload while pending | `ContinuityStore` reloads from `KvStore`; engine seeds by hash | Outbox survives |
| Authentication expires | `authentication_required`; payload preserved | No unauthorized upload, no deletion |
| Authentication restored | Next `synchronize()`/`processOutbox()` resumes | Pending work replays |

---

## 3. Guarantees and how they are met

- **Local functionality remains available.** Continuity observers are called after the authority's local persist/notify; they have no ability to roll back the write.
- **Pending work survives restart.** The outbox is serialised into the existing `KvStore` before any network call. The deterministic reload test asserts the operation count is preserved.
- **Authentication loss never destroys pending changes.** `markUnavailable()` changes state and error only; it does not filter the outbox.
- **Reconnect does not overwrite newer local state.** Pull compares `lastSyncedHash`, current `hash`, and the cloud revision. A both-changed state creates a conflict.
- **Repeated reconnect does not duplicate records.** Stable ids plus idempotency keys and conditional updates; the lost-ack test asserts one cloud row.
- **Partial sync does not produce a false global synced status.** `status()` reports per-authority counts and any pending/conflict/failed state; `localOnly` is true while pending or conflicts exist.
- **Each authority reports its own state.** `ContinuityStatus.authorities[]` is built from the adapter list and per-authority metadata.
