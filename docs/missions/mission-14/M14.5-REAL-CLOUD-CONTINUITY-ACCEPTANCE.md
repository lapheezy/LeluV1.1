## 1. What changed

### 1.1 Strict atomic revision

New migration [`202611160001_continuity_revisions.sql`](../../../supabase/migrations/202611160001_continuity_revisions.sql):

- adds `continuity_revision bigint not null default 1` to `projects`, `conversations`, `knowledge_items` and `user_preferences`;
- installs `lelu_continuity_touch()` as a `BEFORE INSERT OR UPDATE` trigger;
- starts at 1, increments exactly once per update, and sets `updated_at := clock_timestamp()`;
- prevents the client from choosing the new revision.

The adapter conditions on `continuity_revision` when present and uses a namespaced `rev:<n>` token. It accepts legacy `updated_at` bases (`ts:<timestamp>` or plain M14.4 timestamps) only for a project without the migration. This directly repairs the M14.4 same-millisecond/client-timestamp weakness instead of adding another persistence mechanism.

### 1.2 Real adapter defects repaired

| Defect | Repair |
|---|---|
| Lost insert acknowledgement became a false conflict | Identical content is treated as applied, not conflicting |
| Lost update acknowledgement with an old base became a conflict | Identical content is applied again without a revision bump |
| First sync of a hydrated cloud record queued `expected: null` | First observation adopts the cloud record or rebases a genuinely newer local edit |
| A pre-engine local edit was dropped | Newer local content is rebased onto the observed cloud revision |
| A different record in the same JSON document caused a conflict | Unrelated-record changes rebase using `baseRecordHash`; a changed target record still conflicts |
| Zero-row conditional delete was reported as applied | Delete checks affected rows and verifies the tombstone |
| 401/403 looked like a generic retry | Session/auth errors return `authentication_required`; no request without a session |
| Message retry could overwrite newer content | `ignoreDuplicates` on the message upsert |

### 1.3 Passwordless email authentication

All three browser surfaces now use Supabase's normal email sign-in flow:

- the sign-in gate asks only for an email address;
- `SupabasePersistence.requestEmailSignIn()` calls `signInWithOtp` with `shouldCreateUser: true` and a same-origin redirect;
- the project's Auth settings remain authoritative — if sign-up is disabled, the returned message says so;
- an optional one-time code can be verified with `verifyOtp` when the project's email template includes one;
- expired, cancelled, rate-limited and disabled-sign-up outcomes have non-sensitive messages;
- callback diagnostics never expose an access/refresh token, and the URL fragment is not retained;
- no password field, password variable or password fallback remains in the gate, Genesis settings, OG settings or acceptance harnesses.

The dedicated contract tests are in [`tests/email-auth.test.ts`](../../../tests/email-auth.test.ts).

### 1.4 Preserved constraints

- The M14.4 engine and local-first runtime are preserved.
- Supabase remains optional; boot with no configuration produces `Cloud sync off`.
- No new persistence framework, graph database, LangChain/LangGraph or Anthropic dependency.
- Local writes still complete before continuity runs.
- Existing M14.3/M14.4 history was not rewritten; the branch starts at the exact M14.4 head.

`.env.local` has unrelated provider keys only and no Supabase values. The built-in public key belongs to production (`nrehsldbfxthspikaxvr`) and is rejected by the test project with HTTP 401; it was not used. Nothing was read from `.env.local` verbatim.

The supplied address had no matching application Auth user according to the owner's read-only lookup. No user was inserted into `auth.users`; the flow can create one only through Supabase's normal sign-up-capable OTP path if the project permits it.

A real authenticated test still requires the test project's publishable key. Once it is present, the passwordless flow needs one inbox approval in the visible harness browser. Fabricating a JWT, inserting an Auth user directly, or calling a fixture "real cloud" would violate the evidence rules, so WP03–WP06 remain BLOCKED.

## 6. Limitations and residual risks

1. **Real PostgREST semantics are unproven.** The adapter expects a conditional update/delete matching zero rows to be detectable; only a fake client verified that here.
2. **Migration verification is external.** The owner reports it applied on `lelu-v11-test`; this workspace cannot introspect it without the key. The timestamp fallback remains for any project without it.
3. **Messages have no independent revision.** The conversation row is the conditional boundary.
4. **Shared document revision.** Document-backed authorities use one row revision; rebasing is allowed only when the target record's hash is unchanged.
5. **OG server writer.** A direct server update/delete can race the browser continuity path.
6. **Two profiles are not two devices.** Even once run, the harness does not prove mobile suspension, storage eviction or device clock skew.
7. **Email verification needs a human.** The passwordless harness cannot read the supplied Gmail inbox; it waits for the normal link to be opened in its visible browser. A headless cloud run therefore remains blocked even after the key is supplied.
8. **No real-cloud performance.** Only local deterministic microbenchmarks and offline browser timings exist.
