# M14.5 WP05 — SESSION EXPIRY AND NETWORK RECOVERY

**Status:** PARTIAL — local classification and durable outbox retention are VERIFIED; real session/network recovery is BLOCKED.  
**Evidence:** [`real-cloud.json`](../../../artifacts/m145/real-cloud.json), [`supabase-continuity-transport.test.ts`](../../../tests/supabase-continuity-transport.test.ts).

---

## 1. Local guarantees

The continuity engine already provides the important local invariants, and M14.5 preserved them:

- a local write completes before continuity runs;
- a pending operation is durable in `lelu.continuity.sync.v1`;
- an expired session marks work `authentication_required` and stops the batch;
- a network failure marks work `cloud_unavailable` and stops the batch;
- no tight retry loop (1 s → 60 s bounded backoff);
- a reload preserves pending work;
- a stale acknowledgement cannot mark a newer revision synchronized;
- an unauthenticated process cannot reach a cloud write.

M14.5 adds explicit 401/403/PGRST301/42501 classification. A signed-out write now returns `authentication_required`, not a generic retry.

## 2. What the fake contract proves

- a missing session performs no request;
- a 401 response produces `authentication_required`;
- an identical retry after an acknowledged-then-lost write is applied once;
- an old base revision cannot overwrite a newer row.

## 3. What the real harness will prove

`scripts/verify-m145-real-cloud.ts`:

1. signs in;
2. writes a row;
3. signs out;
4. attempts a new write and requires `authentication_required`;
5. re-signs in with a fresh client from the stored session storage;
6. applies the pending write and requires `applied`.

It does not claim that Supabase revoked a refresh token unless the endpoint actually does so. It records the real error status/message.

## 4. Not tested

- real JWT expiry after its expiry time;
- a network drop after the server committed but before the response;
- a partially completed batch against real network timing;
- Supabase auto-refresh behavior;
- a prolonged offline period followed by token refresh failure.

These are BLOCKED until an isolated project and two accounts are available. No simulation is reported as real session expiry.

## 5. Recovery rule

A recovery must resume from the durable operation's exact local revision and expected cloud revision. It must never reset the outbox or assume success from a generic HTTP 200. The adapter only removes the operation after an acknowledgement for the exact local revision.
