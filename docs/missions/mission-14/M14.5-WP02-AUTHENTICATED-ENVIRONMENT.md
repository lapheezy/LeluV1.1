`scripts/verify-supabase-test-project.mjs` names a test project ref and requires `.lelu-runtime/test-supabase.env`; that file does not exist. The harness therefore cannot sign in without inventing an identity, which the mission forbids.

## 2. Opt-in configuration behavior

This is the behavior that must remain true, and is covered by the existing unit tests:

- with no URL and key, `resolveSupabaseConfig()` returns `null`;
- `SupabasePersistence.initialize()` reports `disabled` and creates no client;
- no auth probe, no REST request and no continuity transport are started;
- a URL without a key, or a key without a URL, is reported as missing that half;
- the built-in public project is used only with `SUPABASE_USE_PUBLIC_DEFAULT=true`;
- a secret/service-role value is refused as a browser key.

That was re-confirmed by the production offline harness: the app booted with `Cloud sync off`, zero Supabase attempts, and all local records intact.

## 3. Required isolated environment

To execute WP03–WP06, create an isolated test project (never production) and place these names in `.lelu-runtime/m145-supabase.env`, which is gitignored:

```text
LELU_M145_SUPABASE_URL=https://<test-ref>.supabase.co
LELU_M145_SUPABASE_PUBLISHABLE_KEY=<publishable key for that test project>
LELU_M145_EMAIL=<test account email>
LELU_M145_PASSWORD=<test account password>
LELU_M145_PROJECT_REF=<test-ref>
LELU_M145_ALLOW_REAL=1
```

Optional second account:

```text
LELU_M145_SECOND_EMAIL=<second test account email>
LELU_M145_SECOND_PASSWORD=<second test account password>
```

Apply every migration, including `202611160001_continuity_revisions.sql`, through the project's normal migration process. The harness refuses to run unless the URL contains `LELU_M145_PROJECT_REF` and `LELU_M145_ALLOW_REAL=1`.

Do not put any value into source, a report, a screenshot, a log or this document. Do not use production credentials for destructive testing.

## 4. Why this is BLOCKED, not simulated

A real authenticated test needs:

- a real Supabase auth endpoint issuing a session;
- real RLS evaluation against `auth.uid()`;
- the actual tables and the new revision trigger;
- a real second session for conflict work.

A local fixture or a fabricated JWT cannot prove any of those. The M14.4 fixture remains useful for regression, but it is not relabelled as real cloud acceptance.
