## 1. What was traced

The production path is:

1. authority persists locally and emits a continuity signal;
2. `ContinuityEngine` records a local revision and durable outbox operation;
3. `SupabaseContinuityTransport.push` reads the current cloud row/document;
4. the write is conditional on the revision the client observed;
5. `SupabasePersistence.continuitySession()` supplies the authenticated client when connected;
6. a result is only applied to the sidecar for the exact local revision.

The audit covered:

- `src/core/sync/{ContinuityTypes,ContinuityStore,ContinuityEngine,AuthorityAdapters,SupabaseContinuityTransport}.ts`
- `src/core/persistence/SupabasePersistence.ts`
- `src/core/persistence/PersistenceState.ts`
- `supabase/migrations/202608240001_lelu_runtime.sql`
- `supabase/migrations/202608240002_project_metadata.sql`
- the OG conversation server functions, which are a separate writer path

RLS is a single owner policy on each table:

```sql
using (user_id = auth.uid())
with check (user_id = auth.uid())
```

There was no trigger that owned `updated_at` or maintained a revision.

## 3. Conditional-write findings

M14.4 used:

```js
.update(row)
.eq("id", id)
.eq("user_id", userId)
.eq("updated_at", existing.updated_at)
```

This is a real conditional predicate, but it is not a strict compare-and-swap token:

1. **Same-millisecond collisions.** Two clients can produce the same `updated_at`. Both conditions can match; one overwrites the other.
2. **Client-supplied timestamp.** The update payload includes the client's `updated_at`; it can fail to advance, so a later stale client can match again.
3. **Zero-row outcomes.** M14.4 did not inspect affected rows for deletes, so a delete that matched nothing could be reported as applied.
4. **RLS versus missing row.** A 401/403 was treated as a generic retry rather than an expired/unauthorized session.
5. **Lost insert acknowledgement.** Re-delivery of an insert found the existing row and returned a conflict, despite identical content.
6. **Lost update acknowledgement.** Re-delivery with the old expected revision found newer content equal to the payload and returned a conflict.
7. **First observation.** A device that hydrated a cloud record seeded it as a new local revision and queued an upload with `expected: null`, guaranteeing a false conflict.
8. **Document contention.** A different record in the same `user_preferences` document changed the row revision; the target record was still at its base and should have rebased instead of conflicting.
9. **Message retry.** Messages were upserted without duplicate protection after a row acknowledgement; a retry could overwrite a newer message body.

## 4. Correction

Migration [`202611160001_continuity_revisions.sql`](../../../supabase/migrations/202611160001_continuity_revisions.sql):

- adds `continuity_revision bigint not null default 1` to `projects`, `conversations`, `knowledge_items`, `user_preferences`;
- installs `lelu_continuity_touch()` as a `BEFORE INSERT OR UPDATE` trigger;
- sets the revision to 1 on insert;
- increments exactly once on update;
- sets `updated_at := clock_timestamp()` on the server;
- refuses the client any control over the new revision.

The adapter uses:

```js
.eq("continuity_revision", observed.continuity_revision)
```

when the column is present. It falls back to `updated_at` only for a project that has not applied the migration. Tokens are namespaced (`rev:<n>` or `ts:<timestamp>`); plain M14.4 timestamps remain accepted as legacy bases.

## 5. Defects repaired

- Lost insert and update acknowledgements are idempotent when the content is identical.
- First-seen cloud records are adopted, or rebased when a local edit is newer.
- Conditional deletes verify that a row was actually removed.
- 401/403/PGRST301/42501 are `authentication_required`.
- Document writes rebase when only an unrelated record changed.
- Conversation retries use `ignoreDuplicates` for messages.
- One-row conditional updates return the new token; the old client-supplied timestamp cannot preserve a stale base.

## 6. Residual limits

- The migration must be applied to the real project before strict atomic acceptance.
- Messages have no independent revision; the conversation row is the conditional boundary. A message-only write still changes the conversation row through the canonical store.
- `SupabasePersistence` still has older direct-write helpers for authorities outside continuity (`agents`, `ui_state`, `improvements`, identity documents) and a now-unused public `persistKnowledge`; those are documented in WP07 rather than silently treated as conditional.
- The OG server functions (`src/og/lib/conversations.functions.ts`) update/delete conversations directly. They are a separate server surface and are not routed through `ContinuityEngine`; this remains a real concurrency gap for that surface.
- Real Supabase behavior, RLS rejection and migration application are not tested because no isolated credentials exist.
