# M14.4 — WP02 Revision and Synchronization Contract

**Status:** VERIFIED for the six authorities in the continuity scope; existing non-scoped paths documented in WP01.  
**Implementation:** `src/core/sync/ContinuityTypes.ts`, `ContinuityStore.ts`, `ContinuityEngine.ts`.

---

## 1. Why a sidecar contract

The existing authorities already persist records, but most have no separate revision field. Adding columns to unrelated schemas would have been a migration project and would have made the record content itself responsible for transport state.

M14.4 keeps record content untouched and stores continuity metadata beside it:

```text
lelu.continuity.sync.v1
  records[]   localRevision, lastSyncedRevision, lastSyncedHash,
              hash, cloudRevision, state, lastAttemptAt, lastError
  outbox[]    durable pending operations
  conflicts[] local/cloud snapshots and resolution state
```

The metadata key is `(authority, record id)`. It is not a second record store: `payload.data` is only the snapshot needed to retry a write, and the authority remains the source read by the UI and cognition.

---

## 2. Required fields, and what each authority actually receives

| Field | Implementation |
|---|---|
| Stable canonical id | The authority's existing id (`LeluProject.id`, `ChatConversation.id`, `KnowledgeEntry.id`, `SpatialObject.id`, room id, graph `"graph"`) |
| Record type | `ContinuityAuthority` (`projects`, `conversations`, `knowledge`, `knowledgeGraph`, `spatialObjects`, `cosmosNavigation`) |
| Owning authority | Same enum; adapters read/apply through that store |
| Local change marker | `localRevision`, incremented by the engine per changed content hash |
| Cloud change marker | `cloudRevision`: the actual `updated_at` returned by Supabase, or the `user_preferences.updated_at` for documents |
| Last locally modified | `updatedAt` from the authority record |
| Last synchronized revision | `lastSyncedRevision` |
| Last synchronized content | `lastSyncedHash` |
| Tombstone | `ContinuityRecord.deleted`; currently emitted by `SpatialObjects.remove` and carried for archived Cosmos rooms |
| Sync state | `ContinuitySyncState` below |
| Provenance | Preserved inside `payload.data`; the engine adds no record fields |
| Conflict metadata | `ContinuityConflict` with local/cloud snapshots and reason |

Not every authority gets every field: the nine-state sync enum is shared, but project records do not acquire message fields, and the graph keeps its own revision inside its envelope.

## 3. Sync states

| State | Meaning |
|---|---|
| `local_only` | No cloud revision has been acknowledged for this record |
| `pending_upload` | A local revision is queued and eligible |
| `uploading` | A transport call is in flight for a specific local revision |
| `synced` | The transport acknowledged **that exact** local revision |
| `pending_download` | Reserved for a future pull-only authority; not currently emitted |
| `conflict` | Local and cloud both changed since the last synchronized base; no silent choice made |
| `retry_required` | A bounded retry is scheduled |
| `authentication_required` | No authenticated session; pending work retained |
| `cloud_unavailable` | Network/cloud unavailable; pending work retained |

---

## 4. Rules the engine enforces

1. **Local writes succeed first.** `ContinuitySignals` is called after the store has already persisted and notified. A continuity failure cannot roll back or delay a project, chat, knowledge or spatial write.
2. **A local change advances a distinguishable revision.** The engine hashes the meaningful content (stable key ordering, with transport timestamps/visit counters excluded) plus the tombstone flag. A touch that changes only `updatedAt` does not advance; a real content change does.
3. **Acknowledgements are revision-specific.** `processOutbox` only marks `synced` when `meta.localRevision === operation.localRevision`. An older acknowledgement removes the old operation but leaves the newer revision pending.
4. **Stale work is not uploaded.** Before sending, an operation older than the current local revision is dropped. A newer local operation supersedes an older queued one; an in-flight older operation is allowed to finish so its acknowledgement can be discarded safely.
5. **A failed upload keeps the pending change.** `retry_required`, `authentication_required` and `cloud_unavailable` all retain the payload.
6. **Repeated operations are idempotent.** The operation id and `idempotencyKey` are stable (`authority:recordId:rN`). Duplicate delivery returns the same applied result; the simulated transport and the Supabase adapter both avoid a second destructive write.
7. **Cloud is compared against the last synchronized base.** `pullAll` compares `lastSyncedHash`, current `hash`, and the remote revision before applying anything.
8. **Destructive replacement is gated.** A mismatch creates a conflict and removes the operation; nothing overwrites until `resolveConflict` chooses `keep_local`, `keep_cloud`, or a safe `merge`.
9. **Deletion is explicit.** Only authorities that support it emit `deleted`; absence of a remote record is never interpreted as deletion.
10. **Existing records get a compatibility path.** On first start, records without metadata are seeded with `localRevision = 1`, `lastSyncedRevision = 0`, a content hash, and a pending operation. Existing readable data is never rewritten by the migration.

## 5. Cloud revision acquisition

| Authority | Expected cloud revision | Write condition |
|---|---|---|
| Projects | `public.projects.updated_at` | `.eq("updated_at", existing.updated_at)` |
| Conversations | `public.conversations.updated_at` | `.eq("updated_at", existing.updated_at)`; messages upsert only after the conversation row is accepted |
| Knowledge | `public.knowledge_items.updated_at` | `.eq("updated_at", existing.updated_at)` |
| KnowledgeGraph | `user_preferences.updated_at` for `lelu_sync_knowledge_graph` | `.eq("updated_at", observed)` |
| SpatialObjects | `user_preferences.updated_at` for `lelu_sync_spatial_objects` | `.eq("updated_at", observed)` |
| CosmosNavigation | `user_preferences.updated_at` for `lelu_sync_cosmos_rooms` | `.eq("updated_at", observed)` |

A missing row with a non-null expected revision is a conflict (the cloud copy disappeared). A duplicate insert is a conflict, never an instruction to overwrite.

## 6. Compatibility and limitations

- Records created before M14.4 remain readable and are adopted on first observation.
- The local authority is never cleared by continuity.
- `updated_at` is a timestamp, not a per-write sequence. Two writes in the same millisecond could evade detection; this is a known limitation of the existing schema, not a claim of perfect ordering.
- The graph and spatial documents are one row per authority. Per-object revisions are preserved inside the document, but the row-level condition protects the document as a whole. A conflict on one object therefore blocks document upload until resolved.
- Development identity records are deliberately outside this contract and keep their existing newer-wins merge.
