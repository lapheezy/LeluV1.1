# M14.5 WP03 — REAL CLOUD UPLOAD AND DOWNLOAD

**Status:** BLOCKED for real Supabase; the transport contract is VERIFIED against an in-memory PostgREST stand-in.  
**Evidence:** [`supabase-continuity-transport.test.ts`](../../../tests/supabase-continuity-transport.test.ts), [`real-cloud.json`](../../../artifacts/m145/real-cloud.json).

---

## 1. What the real harness will do

`scripts/verify-m145-real-cloud.ts` obtains one real session through the app's passwordless email flow, restores it into two independent Supabase clients, and exercises the production `SupabaseContinuityTransport`:

| Step | Check |
|---|---|
| 1 | Insert a project from session A; require `applied` |
| 2 | Pull the project from session B; require the same name |
| 3 | Read the database row independently; require the same name |
| 4 | Re-deliver the insert; require the same revision and one row |
| 5 | Update from A conditionally; require the next revision |
| 6 | Attempt a stale update from B; require `conflict` and the cloud version |
| 7 | Apply a resolved revision; require `applied` |
| 8 | Insert a conversation and message; pull from B |
| 9 | Insert knowledge; pull from B |
| 10 | Insert a graph document; retry; pull from B |
| 11 | Insert two spatial records, rebase one, pull from B |
| 12 | Insert a Cosmos room document; pull from B |
| 13 | Sign out A locally; require `authentication_required` on write |
| 14 | Restore A from the still-valid session; require the pending write to apply |
| 15 | When a second account exists, require RLS isolation |

The script removes only the rows it created and restores pre-existing documents. It never prints the URL key, email, password or session token; there is no password input at all.

## 2. What is verified without the cloud

The in-memory contract tests exercise the actual adapter code, not `SimulatedTransport`:

- insert → applied with `rev:1`;
- lost insert acknowledgement → applied again, one row, no revision bump;
- conditional update → `rev:2`;
- stale update → conflict, with the remote version;
- duplicate update → applied, no false conflict;
- expired session → `authentication_required`;
- missing session → no write;
- graph document retry → one document, same revision;
- two spatial records in one document → both retained;
- unrelated document revision change → target-record rebase;
- changed same-record document → conflict;
- pull accepts both `rev:` and legacy `ts:` tokens.

## 3. What is not verified

- actual Supabase REST/PostgREST behavior;
- the migration applied to a real project;
- actual RLS evaluation;
- actual `user_preferences` document size/growth;
- actual network latency, retries and auth refresh;
- actual server timestamps and revision increments.

These are **BLOCKED**, not passed by the in-memory tests.

## 4. Procedure

Start the app with the isolated project's URL/key, then run with a visible browser and complete the normal email link:

```bash
LELU_M145_HEADFUL=1 npx tsx scripts/verify-m145-real-cloud.ts
```

The script writes `artifacts/m145/real-cloud.json`. A BLOCKED artifact means no request was made.
