## 2. How the real conflict test works

`scripts/verify-m145-real-cloud.ts`:

1. inserts a project from A;
2. both sessions observe revision `rev:1`;
3. A writes `Device A edit` conditionally;
4. B writes `Device B stale edit` with the old `rev:1`;
5. requires B to receive `conflict` and the remote name `Device A edit`;
6. applies B's resolved revision against the new cloud token;
7. verifies the final row through an independent query.

For spatial data it inserts record A, then record B in the same document, then moves A with an old document token and its base record hash. It requires the unrelated change to rebase rather than conflict.

## 3. Strictness of the condition

The M14.4 `updated_at` condition was not sufficient as a strict token. M14.5 adds a server-owned `continuity_revision` and conditions on that:

```sql
where id = $1 and user_id = auth.uid()
  and continuity_revision = $observed
```

The trigger increments the revision, so two writes based on the same observed revision cannot both match. The adapter returns a conflict and the remote snapshot when the condition matches zero rows.
