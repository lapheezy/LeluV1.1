# M14.4 — WP04 Conflict Detection and Resolution

**Status:** VERIFIED for project, conversation and spatial record conflicts in deterministic tests. Real cloud conflict traffic is **BLOCKED** by missing credentials.
**Implementation:** `ContinuityEngine`, `AuthorityAdapters`, `ContinuityTools`.

---

## 1. Detection rule

A conflict exists when **both** sides changed since the last synchronized base:

```text
localChanged  = localRevision !== lastSyncedRevision
             OR (lastSyncedHash !== null AND hash !== lastSyncedHash)

remoteChanged = remote.cloudRevision !== null
             AND remote.cloudRevision !== meta.cloudRevision
```

If the remote content is byte-identical to the last synchronized value, the local revision is allowed to upload against that cloud revision. If both changed and neither side equals the last synchronized content, the engine records a conflict and **does not upload**.

A separate push conflict is produced by the transport when:

- the cloud row's current `updated_at` no longer equals `expectedCloudRevision`;
- a record the client believed existed is gone;
- an insert collides with an existing id;
- a stale device uploads an old revision.

A conflict is never represented as `synced`. The conflict record contains both snapshots, the authority, both revisions, the reason and the resolution state.

## 2. Policies by data type

| Authority | Policy | Automatic merge? | Why |
|---|---|---|---|
| Projects | Detect and preserve both | No | Two project edits can change name, items, schedule, tasks and objective independently. No field-level authority exists |
| Conversations | Conditional row + append-only message union | Yes, for message identity only | Messages have stable ids and timestamps. The later conversation metadata is retained; messages are unioned and sorted. A conversation row is not replaced by a stale whole snapshot |
| Knowledge library | Detect and preserve both | No | Free-text detail plus a status; no provenance hierarchy that makes a field merge safe |
| KnowledgeGraph | Detect and preserve both | No | Nodes/edges have stable identity, but a changed node has no field-level winner. Forced replacement would be an unsafe graph merge |
| SpatialObjects | Detect and preserve both | No | Concurrent transforms of the same object are a real disagreement; object identity must not be duplicated |
| CosmosNavigation | Additive room union | Yes, for distinct rooms | Rooms have stable ids and additive semantics; a missing room in one snapshot does not delete it |
| Identity / security records | Existing newer-wins path retained | Not by continuity | Security-sensitive; arbitrary last-writer-wins is not acceptable, and M14.4 does not pretend to resolve it |

## 4. Resolution

`ContinuityEngine.resolveConflict(id, resolution)` and the `continuity.resolve` tool expose three choices:

### `keep_local`

- Preserves the local snapshot.
- Advances the local revision.
- Sets `expectedCloudRevision` to the cloud revision that caused the conflict.
- Queues a new conditional upload.
- The original conflict record is retained as `resolved` with both versions.

### `keep_cloud`

- Applies the cloud snapshot through the authority's own apply path, with `force: true`.
- Marks the local revision synchronized against that cloud revision.
- Refuses when the cloud side is a deletion; the user must choose local or an explicit merge.
- The conflict record is retained as `resolved`.

### `merge`

- Uses the adapter's narrow merge only.
- Conversations: union messages by stable identity.
- Cosmos rooms: union by room id.
- All other authorities return `null`; the call is refused with an explanation and the conflict remains open.
- A merged result is uploaded conditionally using the conflict's cloud revision.

A resolved conflict is **not** deleted. It remains recoverable in the conflict log.

---

## 5. User-facing surface

`PersistenceStateStore` reads `ContinuityEngine.status()` and, when unresolved conflicts exist:

- changes the status label to **Conflict**;
- keeps the mode `degraded`;
- appends the pending/conflict count to the existing detail string;
- states that the record is not considered synchronized until resolved.

No separate conflict UI subsystem was introduced. The same existing status facade is used. The model-facing `continuity.status` and `continuity.resolve` tools read and resolve the same records through the existing dispatcher.

---

## 6. What is not merged

- Projects, knowledge entries, graph nodes and spatial transforms are intentionally left unresolved until a human or explicit decision. A timestamp is not permission to overwrite.
- Identity records are not auto-merged by the engine.
- Forge placements and `SpatialSceneGraph` are out of scope.
- Agent/question/UI/improvement paths retain their existing semantics; M14.4 does not claim conditional conflict handling for them.
