# M14.4 — WP06 Cosmos, Spatial Objects and Forge Continuity

**Status:** SpatialObjects and Cosmos room continuity **VERIFIED** deterministically. Forge placements and `SpatialSceneGraph` are **EXPLICITLY EXCLUDED** with reasons.  
**Implementation:** `SpatialObjects`, `CosmosNavigation`, `AuthorityAdapters`, `SupabaseContinuityTransport`.

---

## 1. Authorities and boundaries

| Authority | Persisted? | Record | M14.4 behaviour |
|---|---|---|---|
| `SpatialObjects` | Yes (`lelu.cosmos.objects.v1`) | Placement pointer: stable `id`, `link {kind,id}`, room, position, pin, note, timestamps | Per-object conditional sync |
| `CosmosNavigation` | Yes (`lelu.cosmos.nav.v1`) | User/LÉLU rooms, visits, trail | Revisioned room-set document; additive union |
| `SpatialSceneGraph` | **No** | In-memory scene nodes and optimistic revisions | Excluded; ephemeral rendering state |
| `SpatialObjectRegistry` | **No** | In-memory registry | Excluded |
| `ForgeClient` placements | Server-owned `/api/forge/placements` | Server placement | Excluded; the server is the authority |
| Camera animation / transient UI | No | Ephemeral | Excluded |

A spatial object is a pointer, never a copy of the source record. Synchronizing its position does not duplicate the message, document, image or project it points at.

## 2. SpatialObjects continuity

### Identity

`SpatialObject.id` is the record id. Placement is idempotent by `link.kind + link.id`, so the same record dropped twice updates the existing object instead of creating a second one. The continuity layer preserves that identity across devices.

### Local write paths

- `place` → local persist + signal
- `move` / `pin` → local persist + signal
- `remove` → local delete + tombstone signal
- `restore` → local snapshot persist

### Cloud representation

Existing `user_preferences` document:

```text
preference_key: lelu_sync_spatial_objects
value.records: [ { id, updatedAt, data: SpatialObject, deleted? }, … ]
```

The document has a conditional `updated_at`. A record's position is only replaced after the conditional document write succeeds.

### Required scenarios

| Scenario | Result |
|---|---|
| Create a spatial object offline | VERIFIED: local write; pending operation |
| Modify its transform offline | VERIFIED: `move` advances local revision |
| Reload and recover the object | VERIFIED: new `SpatialObjects` instance hydrates `KvStore` |
| Queue eligible cloud operation | VERIFIED: outbox snapshot contains object id and position |
| Reconnect and synchronize | VERIFIED deterministically with `SimulatedTransport` |
| Detect concurrent cloud transform | VERIFIED: same object id with different positions becomes a visible conflict |
| Preserve object identity | VERIFIED: stable id and link; no duplicate placed object |
| Prevent duplicate object creation | VERIFIED: placement idempotent by link; repeated sync by id |
| Deletion/archival | VERIFIED for local remove/tombstone path; cloud conditional delete is implemented for table-backed authorities, document tombstones are carried for spatial objects |
| Rebuild derived view | Derived Cosmos view reads `SpatialObjects`; no separate persistent index |

### Conflict example

The deterministic test creates an object, synchronizes it, writes a cloud transform `[9,9,9]` through the simulated transport, moves locally to `[5,5,5]`, synchronizes, and asserts:

- a conflict exists;
- local position is `[5,5,5]`;
- cloud position is `[9,9,9]`;
- resolution `keep_local` uploads `[5,5,5]` conditionally;
- the object list still contains exactly one object with that link.

## 3. CosmosNavigation continuity

Only rooms created by the user or LÉLU are persisted; system destinations are re-registered from the runtime on every boot. The continuity document therefore carries only non-system rooms.

- `removeRoom` archives rather than deletes; the archived flag travels in the document.
- `restoreRoom` clears the flag and advances the document.
- Navigation visits and the trail remain local presentation state; they are not synchronized as canonical records. This prevents a device's current viewpoint from overwriting another device's map.
- Applying remote rooms is a union by room id. A room missing from one snapshot is not deleted; an explicit archived flag is required.
- A concurrent room-set edit is resolved by additive merge; room labels remain the local authority for an existing id.

---

## 4. Forge placements

`ForgeClient` calls the server's `/api/forge/placements`; placement ownership, identity and deletion are server-side. Adding a local continuity mirror would create a second authority and could resurrect a placement the server deleted. It is excluded.

If a future mission makes placements local, it must first establish a local canonical record and a server-side conditional revision. M14.4 does not pretend that boundary is solved.

---

## 5. SpatialSceneGraph

`SpatialSceneGraph` holds an in-memory, revisioned scene with optimistic commits. It is not backed by `KvStore`, contributes no durable user record, and is rebuilt by the scene runtime. Synchronizing it would upload ephemeral renderer state and would create a competing scene authority.

The persisted placement authority is `SpatialObjects`. That is the record M14.4 synchronizes.
