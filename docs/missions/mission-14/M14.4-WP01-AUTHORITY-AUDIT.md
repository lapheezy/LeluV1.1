# M14.4 — WP01 Persistence Authority Audit

**Mission:** 14.4 — Local-first continuity, synchronization and conflict resolution
**Baseline:** `mission-14.3/independent-runtime-acceptance` at `9363966`
**Audit basis:** source inspection at the baseline plus the M14.4 implementation in `src/core/sync/`.
**Status:** VERIFIED for the inspected authorities; ambiguous mappings are explicitly excluded below.

---

## 1. The rule that shaped the audit

Every authority in this repository already owns a record shape, an identifier and a local write path. Mission 14.4 does **not** replace any of them. The continuity layer is sidecar metadata keyed by `(authority, record id)`, plus a durable outbox and a conflict log in the existing `KvStore`.

No new database, graph store, memory system or persistence framework was introduced.

The central distinction:

| Layer | Owner | Role |
|---|---|---|
| Record content | Existing authority (`ProjectStore`, `MultiChatStore`, `KnowledgeLibrary`, `KnowledgeGraph`, `SpatialObjects`, `CosmosNavigation`, …) | Canonical local truth |
| Continuity metadata | `ContinuityStore` (`lelu.continuity.sync.v1`) | local revision, last acknowledged cloud revision, hash, state |
| Cloud mirror | Existing Supabase tables and existing `user_preferences` documents | Optional, conditional mirror |
| Derived presentation | Neural Map / Cosmos visuals / UI | Read-only projection, never a sync authority |

## 2. Authority inventory

### 2.1 Projects and development records

| Field | Finding |
|---|---|
| Authority | `ProjectStore` |
| Identifier | `LeluProject.id` (UUID) |
| Local storage | `KvStore` key `projects.v1` (physical key `lelu.projects.v1`) |
| Cloud representation | `public.projects` (`id`, `user_id` primary key; `updated_at`; `metadata` jsonb) |
| Existing revision | `updatedAt` milliseconds; no separate revision column |
| Provenance | Project fields plus `metadata` request fields; no author field |
| Updates | `create`, `update`, item/agent operations → `persist()` |
| Deletes | `archive` changes status; `remove` deletes the local record |
| Existing sync | `SupabasePersistence.attachRuntime()` previously subscribed and blind-upserted every snapshot |
| Conflicts | None. Last writer won. M14.4 now uses conditional `updated_at` writes through `ContinuityEngine` |
| Offline | Yes, fully local |
| M14.4 mapping | Per-project records; conflict requires explicit resolution; no automatic project merge |

Development records (`LeluIdentity`, `DailyRecord`, `CuriosityLedger`) use their own `KvStore` keys and existing per-user documents in `user_preferences`. They retain their existing newer-wins merge behavior. They are **security-sensitive identity records** and are not auto-merged by the M14.4 engine.

### 2.4 Local cognition KnowledgeGraph

| Field | Finding |
|---|---|
| Authority | `KnowledgeGraph` |
| Identifier | Node `id`; edge key `${from}-${to}-${relation}` |
| Local storage | `KvStore` key `lelu.cognition.knowledge.v1` (module constant; physical key prefixed once by `KvStore`) |
| Cloud representation | **No `knowledge_items` mapping exists.** The two schemas are not interchangeable |
| Revision | Envelope `revision` plus `updatedAt` |
| Provenance | Envelope `provenance: "local"`; node `data` is free-form |
| Updates | `addNode`, `connect` → `persist()` increments revision |
| Deletes | None exposed |
| Conflicts | Local graph is overwritten only by its own `persist()`; no cloud conflict path existed |
| Offline | Yes, this is the canonical local cognition graph |
| M14.4 mapping | Preserved as a separate authority. It is synchronized only as an opaque, revisioned per-user document (`lelu_sync_knowledge_graph`) when cloud continuity is enabled. It is **not** written into `knowledge_items` and is not assumed to be the same data |

**Special investigation result:** `KnowledgeLibrary` is the only authority that writes `knowledge_items`. `KnowledgeGraph` is instantiated by `CognitiveCore` and persists a different envelope (`nodes`, `edges`, `revision`, `provenance`). No consumer, migration or writer treats them as interchangeable. M14.4 therefore does not merge them.

These retained paths are listed honestly. M14.4 does not claim that every existing Supabase writer was converted; it converted the authorities named in its implementation scope and left the others on their existing behavior.

### 2.7 Neural Map

No standalone persistent Neural Map store was found. The map is a derived visualisation over cognition, graph, Cosmos and project authorities. There is no `neural-map` key, no canonical record id and no writer that could become a second sync database.

M14.4 therefore treats Neural Map as **derived state**. It must be rebuilt from reconciled authorities; it is never itself uploaded as canonical data. This is an explicit scope boundary, not an implemented persistent index.

## 4. Existing synchronization paths mapped

Before M14.4:

1. `SupabasePersistence.initialize()` establishes the optional session.
2. `hydrateRuntime()` reads projects, conversations, messages, knowledge, memories, agents, questions, UI state, news, API health and development documents into the canonical stores.
3. `attachRuntime()` subscribes `ProjectStore`, `MultiChatStore`, `KnowledgeLibrary`, agents, questions, UI, improvements, events and development stores.
4. `write()` performs a blind `upsert` with the table's conflict key; failures are contained and reported as degraded.
5. Realtime pulls projects, agents, questions and UI state; `mergeRemote` keeps the newer timestamp.

After M14.4:

- Projects, conversations, knowledge, the local knowledge graph, spatial objects and Cosmos rooms are observed by `ContinuityEngine`.
- The old blind subscriptions for projects, conversations and knowledge are removed from `attachRuntime()`.
- The engine writes a durable operation before attempting network access.
- Cloud writes are conditional on the cloud revision the client last observed.
- A mismatch produces a conflict; it does not overwrite.
- Agent, question, UI, improvement and memory sync remain on their existing paths, explicitly outside this mission's continuity scope.

## 5. Ambiguities and exclusions

1. **`KnowledgeGraph` vs `knowledge_items`:** separate; no automatic mapping. Documented above.
2. **`SpatialSceneGraph`:** in-memory; no persisted record to synchronize.
3. **Forge placements:** server-owned; not a local authority.
4. **Identity records:** security-sensitive; not auto-merged by continuity.
5. **Agents, questions, UI, improvements, memories:** existing sync paths retained; not claimed as M14.4 conditional conflict handling.
6. **Neural Map:** derived, not a persistent authority; no new index was created.
7. **Deletion tombstones:** only `SpatialObjects.remove` and Cosmos room archival emit deletion/archival signals. Other authorities express removal as archive/status or do not expose deletion.
