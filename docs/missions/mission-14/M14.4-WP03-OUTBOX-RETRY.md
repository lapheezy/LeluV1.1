# M14.4 — WP03 Local Outbox, Retry and Idempotency

**Status:** VERIFIED for the deterministic and simulated-transport paths. Real Supabase retry is **BLOCKED** by the absence of an authorized test project.  
**Implementation:** `ContinuityEngine`, `ContinuityStore`, `SimulatedTransport`, `SupabaseContinuityTransport`.

---

## 1. Storage decision

The outbox lives in the existing `KvStore` under `continuity.sync.v1`. It is not a second database and it creates no new dependency. The same serialized state carries the revision ledger, pending operations and conflicts, so a reload cannot observe one without the others.

An operation is written **before** the network call. A failed or interrupted upload therefore leaves a recoverable operation, not a lost mutation.

---

## 2. Operation shape

| Field | Purpose |
|---|---|
| `id` | `authority:recordId:r<localRevision>`; one stable operation per revision |
| `idempotencyKey` | Stable key sent to / recognized by the transport |
| `authority` | Canonical record type |
| `recordId` | Canonical id |
| `type` | `upsert` or `delete` |
| `localRevision` | Exact revision being uploaded |
| `createdAt` | Scheduling order |
| `attempts` | Bounded attempt count |
| `state` | `pending_upload`, `uploading`, `retry_required`, `authentication_required`, `cloud_unavailable`, … |
| `payload` | Exact record snapshot and tombstone flag |
| `expectedCloudRevision` | Last cloud revision observed; conditional write base |
| `lastError` | Honest last failure |
| `nextAttemptAt` | Bounded backoff deadline |

---

## 3. Behaviour by case

### Offline write

The authority persists immediately and emits a local signal. The engine advances the local revision and commits a pending operation to `KvStore`. No network is attempted until a transport reports ready.

### Reconnect

`processOutbox()` observes transport availability. If a session exists, eligible operations are sent in bounded batches (`MAX_BATCH = 20`). A rejected session sets `authentication_required`; a network failure sets `cloud_unavailable`; neither removes the operation.

### Interrupted upload

The transport may throw after a cloud write. The engine converts the throw into `retry_required`, keeps the operation and schedules a bounded retry. The simulated transport deliberately models the write-then-lost-ack case.

### Duplicate delivery

The operation id and idempotency key are stable. Re-delivery before a fresh write returns the previously acknowledged cloud revision. The deterministic test asserts one cloud row after a lost acknowledgement and retry.

### Stale acknowledgement

If revision 2 is committed while revision 1 is in flight, revision 1's acknowledgement removes only the revision-1 operation. Revision 2 remains pending and its state is not marked `synced`. This is directly tested.

### Authentication failure

`authentication_required` is written to the operation and record metadata, with the reason. The outbox is untouched. `markUnavailable` never deletes payloads.

### Cloud unavailable

`cloud_unavailable` is recorded, the current batch stops, and local operation continues. No tight retry loop: retries use bounded backoff (`1s, 2s, 5s, 15s, 30s, 60s`) and a failed batch stops rather than spinning.

---

## 4. Retry bounds and scheduling

- Retries are scheduled with `nextAttemptAt`, not an interval loop.
- A batch stops on authentication loss, cloud unavailability or a retry-required result.
- Operations with a future `nextAttemptAt` are skipped.
- An operation whose local revision is older than the current revision is dropped before upload.
- The outbox is capped at 2,000 operations and conflicts at 200 to keep the sidecar bounded. When the cap is reached the oldest operations are the ones removed; this is a deliberate bounded-storage policy, not silent success.

---

## 5. Idempotency and destructive side effects

`SimulatedTransport` records applied idempotency keys and returns the same `cloudRevision` on duplicate delivery. `SupabaseContinuityTransport` uses conditional updates; a duplicate message upsert is by `(id, user_id)`, so a repeated conversation upload does not append a second message row. Project, knowledge and document inserts use stable ids; a duplicate id surfaces as a conflict rather than a replacement.

No tool execution is performed by the outbox. Syncing a record can never execute a tool or alter protected runtime configuration.
