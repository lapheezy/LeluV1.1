## 6. Test E — multi-device model

**Classification: BROWSER + MULTI-CONTEXT_SIMULATION + SIMULATED_BACKEND, not physical-device acceptance.**

`scripts/verify-m144-multidevice.mjs` was executed against two independent Chromium contexts. Each context had its own `localStorage` and its own continuity metadata. A local fixture server on `127.0.0.1:3101` provided conditional writes and idempotency; it is explicitly not Supabase.

The run:

1. synchronized both contexts;
2. created a project in device A and waited until the fixture cloud held it;
3. synchronized device B and confirmed it saw the same project id;
4. took both contexts offline and edited the same project (`Device A edit`, `Device B edit`);
5. reconnected device A, which uploaded conditionally;
6. reconnected device B, which detected a project conflict with both names intact;
7. resolved `keep_cloud`, after which device B held `Device A edit`.

Result: `status: PASS`, `seenByB` matched the created project, conflict local/cloud names were preserved. Artifact: `artifacts/m144/multidevice-acceptance.json`.

This is not a physical-device test. Real cross-device delivery through Supabase remains BLOCKED.

What is **not** verified:

- two physical browsers signed into the same Supabase account;
- real cross-device delivery through Supabase;
- real device clock skew;
- real network partition/recovery.

These remain part of the BLOCKED cloud criterion.
